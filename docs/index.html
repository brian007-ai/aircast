能做什么

一个手机上就能跑完的投送链路

不是遥控器，也不是中转服务：声音从播放它的那台手机出发，直接进音箱。

任何应用的声音

音乐、播客、有声书、视频、通话 —— 只要它在手机外放，就能被采集投出去。

自动发现音箱

通过 mDNS / Bonjour 扫描 _airplay._tcp，列表里点一下就连；扫不到也可以手输 IP。

音量键交给音箱

投送期间按音量键调的是音箱，不是手机；屏幕上还有 +/− 作为兜底。

手机扬声器同步静音

声音只在音箱里响，不会两边都放。哪些路径能自动恢复、哪些要手动点，文档写得很清楚。

不需要任何主机

没有树莓派、没有 NAS、没有桌面端在后台跑。关掉电脑也照样投。

零云端

没有网络请求以外的东西：除了局域网里的音箱，应用不和任何服务器说话。

工作原理

四步，全部在手机里完成

AudioPlaybackCapture 在 mediaProjection 前台服务里抓 PCM，经 JNI 进环形缓冲， 由原生线程按 AirPlay 2 的节奏推给音箱。协议栈是仓库内自带的 airplay2-sender-cpp。

STEP 01

采集

系统弹出一次录制授权，之后整段会话都在前台服务里抓音频。

STEP 02

过桥

PCM 帧经 JNI 进入环形缓冲，Java 侧不碰音频数据本身。

STEP 03

投送

原生线程把缓冲按 RTP 时间线推给 AirPlay 2 接收端，密钥对在本地派生。

STEP 04

收听

延迟约 2–3 秒，这是 AirPlay 协议自身的缓冲，不是应用额外加的。

两份补丁，换来稳定

HomePod 走的那条配对路径上，上游只派生控制通道密钥，事件通道没被加钥，接收端大约 30 秒后 就会踢掉会话 —— 哪怕音频一直在流。AirCast 在那条路径上把 Events 密钥也派生出来。

时钟漂移

连接阶段把缓冲排到约 0.25 秒，握手不背旧包袱；进入播放后，队列超过 1.6 秒就做一次小幅拼接， 吸收两端时钟差。

界面

一块会呼吸的液态玻璃

整套界面是代码画出来的，没有 XML 布局、没有贴图：半透明圆角板浮在缓慢漂移的极光背景上， 高光带、内阴影、边缘折射和四角聚光都按真实光照算，亮暗跟随系统。

目标选择和动作分离

音箱换用底部浮层，选中就收起；开始/停止永远钉在拇指够得到的地方，不会被滚动带走。

一个状态源

空闲 / 发现 / 连接 / 投送 / 停止 / 出错，六态集中在一个状态机里，通知栏结束的投送也会立刻反映到界面。

为拇指和读屏调过

可点区域最小 48dp，开关向读屏报告真实的选中态，所有文案走资源文件，中英双语。

安装步骤

  1. 用手机打开本页，点上面的下载 APK。
  2. 系统提示"未知来源"时，允许浏览器安装应用。
  3. 装完打开 AirCast，点选择音箱，在浮层里挑你的接收器。
  4. 点开始投送，在系统弹窗里允许录制 —— 这一步平台强制，每次会话一次。
  5. 停止时点屏幕上的停止投送，手机音量会自动恢复。

先说清楚

已知限制

这些不是 bug 列表，是当前版本的边界；写在这里，免得装完才发现。

  • 拒绝被采集的应用只有静音。DRM 与流媒体（Netflix 之类）主动关掉了播放采集，任何应用都抓不到。
  • 按用途采集，不按应用。任何在播媒体音频的应用都会被一起投出去；系统给的"单个应用 / 整个屏幕"选项不会缩小采集范围（本应用从不着录屏幕）。
  • 延迟设置对下一次生效。接收端的抖动缓冲在 SETUP 阶段协商，会话中途改不了。
  • 断线不会自动重连。接收端掉线后需要重新开始一次投送。
  • 音量键可能被别的应用抢走。如果别的应用占着媒体会话，音量键调的可能是它，用屏幕上的 +/−。
  • 实际采样率以系统为准。申请 44.1 kHz 拿到 48 kHz 是常事，应用会读回真实值再对齐节奏。

隐私

不收集，不存储，不上传

没有账号体系，没有统计 SDK，除了和局域网里的 AirPlay 接收器通信，应用不与任何服务器建立连接。 录音权限只用于把声音实时转成投送流，不落盘。
